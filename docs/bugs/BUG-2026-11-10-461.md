## BUG-2026-11-10-461 — a bought lead list with a phone typed as a number refused the whole import (500) `sales-leads` `import` 🟡

`planImport` (`src/lib/lead-import.ts`) read every cell as `(raw.phone ?? "").trim()`. A spreadsheet hands a phone typed without spaces or dashes (`60124567890`) over as a NUMBER, and `.trim()` on a number throws, so `POST /api/sales-leads/import` (dry run included) failed with a 500 for the whole list instead of planning it. The same held for a company name, a location or notes that Excel stored as a number. Found while pinning the lead-list importer to the shared table-import parser (item 121): the parity test's sample file carried one numeric phone and both the old and the new mapping crashed in the planner. Not reproduced against a live server; whether any list was refused this way on prod is UNMEASURED.

Fix: every cell goes through `cellText(v)` — `String(v).trim()`, blank for null / undefined. A text cell comes out exactly as before; a number is read as its digits (the phone key is unchanged, since `normalizePhone` already used `String`).

Regression: `tests/table-import-more-importers.test.mjs` (BUG-2026-11-10-461 block).
