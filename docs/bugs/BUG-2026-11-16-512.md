## BUG-2026-11-16-512 — A sofa's armrests and cushions could go out on a DO before the sofa was ready `delivery` `pending-delivery` 🟡

🟡 **On branch** (`fix/hk0153-sofa-set-accessories` → `main`). Hub ticket HK-0153 (Violet,
16 Nov): "model 8211/8210 binding at delivery order… 1 SO = 1 order".

**Symptom.** Pending Delivery let an operator tick a sofa SO's ready accessories (A01 armrest,
SB02 sandback, BC05-MF back cushion) and issue a DO for them alone while the sofa itself was
still in production. Measured on prod 16 Nov (`GET /api/delivery-orders/ready-planning`):
SO-2610-078's 8211-7FT showed set 3/7, but its two ready A01 rows showed 1/1 and were
selectable; SO-2610-252 the same with SB02 / BC05-MF.

**Cause.** `buildReadyPlanning` (`src/lib/delivery-pipeline.ts`) already counted these
accessories in the sofa's set (they have an UPHOLSTERY card), but gave the set status only to
rows whose category is SOFA. Every ACCESSORY row got `{1/1, setComplete: true}`.

**Fix.** In an SO with an 8211 or 8210 sofa (product code starts with `8211` / `8210`), a row
counted in the set now carries that set's status, whatever its own category. The desktop Set
Status column and the mobile set pill show it on those rows too. Other sofa models and
accessory-only SOs keep shipping accessories per piece (YH, 16 Nov: "only this, they didnt
mention all"). The server still does not refuse a
partial set on `POST /api/delivery-orders`; the gate is the selection, as it was for sofas.

**Regression test.** `tests/delivery-pipeline.test.mjs` "HK-0153" (ready armrest of an
unfinished 8211 / 8210 set is not selectable, which fails on the old code; set complete; a
5540 sofa's armrest and an accessory-only SO still ship per piece) and
`tests/m-do-mobile.test.mjs` (accessory set pill).
