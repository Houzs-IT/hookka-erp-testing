## BUG-2026-11-24-552 — Scan supplier document: PI create failed with "promise was created by a request that has since ended" `procurement` `self-apply` 🔴

- **Symptom (prod, 2026-11-24):** Purchase Invoices > Scan supplier document > Create showed "1 document failed: Database is missing a column and it could not be added: This promise was created by a request that has since ended, so it can never settle."
- **Cause:** `ensurePiMigrations` (`src/api/routes/purchase-invoices.ts`) kept its in-flight self-apply promise in a module variable and handed it to every request. On Workers a promise settles only in the request that made it. When that request ended first (the client gave up, or the request was cancelled), every other request awaiting it got this error. The `.catch` that would clear the memo never ran either, so the isolate could stay stuck until it recycled. The error text comes from the POST `/` catch around the self-apply.
- **Class:** the promise-memo self-apply class in `docs/BUG-CLASSES.md`, defect 2. The earlier fix ("clear the memo on failure") did not cover it, and `memoizeSelfApply` shared the in-flight promise too.
- **Fix:** `memoizeSelfApply` (`src/api/lib/self-apply.ts`) now sets the memo only after the round lands, and never returns the in-flight promise. Two cold requests each run the round; every statement is IF NOT EXISTS. Every hand-rolled promise memo in `src/api` now goes through it.
- **Not fixed:** `stockStatusInflight` (`src/api/routes/mrp.ts`) is a data single-flight with the same hazard. It is listed in the test and left for its own change.
- **Regression tests:** `tests/self-apply-memo-is-boolean.test.mjs`. The source scan now fails on any promise memo not handled by `memoizeSelfApply`. A behavioural test checks that a second caller never gets the first caller's in-flight promise; against the old helper it fails.
