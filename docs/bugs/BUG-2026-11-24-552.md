## BUG-2026-11-24-552 — 1003(A)-(K) used a 2025 demo sofa BOM (productId collision) `bom` `mrp` `inventory` `costing` 🔴

- **Symptom:** MRP spot check (owner 2026-11-24 「你挑5个抽查」): AM275-1 showed 60.48 m needed by 8 open 1003(A)-(K) HILTON(A) 6FT bedframe orders whose fabric is PC151-xx. Each line was 7.56 m = 7 m + 8% — a line of the 5530-1A sofa demo BOM.
- **Cause:** `resolveBomMaterialsRaw` (`src/api/lib/po-cost-cascade.ts`) tries ACTIVE `bom_versions` by **productId** before the product's `bom_templates`. Three 2025 demo rows were still ACTIVE: bom-v-1 (1003-(K), prod-2), bom-v-2 (1003-(Q), prod-2), bom-v-3 (5530-1A sofa, **prod-5**). prod-5 is the real product 1003(A)-(K), prod-2 is 1003-(Q). So 1003(A)-(K) orders took the sofa's materials. The same path feeds MRP, per-WIP RM deduction and costing, so those orders' deductions and cost were wrong too (pre-existing; surfaced by the MRP).
- **Fix:** (1) code: a version found by productId is used only when its productCode matches the order's (else fall back to the template). (2) data, owner-approved 「1、2」 2026-11-24: bom-v-1, bom-v-2, bom-v-3 set OBSOLETE via `PUT /api/bom/:id` (bom-v-4 was already DRAFT). Verified live right after the data change: AM275-1 gone from MRP; 1003(A)-(K) orders now need their own PC151-xx fabric (Divan + Headboard lines).
- **Not done (owner to decide):** correcting stock already deducted / cost already booked for 1003(A)-(K) under the wrong BOM.
- **Regression test:** `tests/bom-version-productid-collision.test.mjs` (fails without the code fix).
