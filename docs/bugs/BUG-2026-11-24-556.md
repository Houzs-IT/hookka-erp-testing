## BUG-2026-11-24-556 — Some self-apply rounds sent raw ALTERs, one set per cold request, after #1593 `accounting` `self-apply` 🟡

- **Symptom (review of #1593, not seen in prod):** since BUG-2026-11-24-553, every request that finds a cold isolate runs its own self-apply round instead of sharing the one in flight. Most rounds go through `runSelfApply`, which reads the catalog and sends only the ALTERs still needed. Some memoized rounds sent `ALTER TABLE … ADD COLUMN IF NOT EXISTS` straight to the database. Postgres takes an ACCESS EXCLUSIVE lock for every ALTER TABLE, even a no-op (BUG-2026-11-21). After a deploy, N concurrent cold requests took about N × 24 locks on `payment_vouchers` (14 + 8 ADD COLUMN, plus the status CHECK DROP and ADD) instead of none.
- **Cause:** `ensurePvApColumns`, `ensurePvApprovalCols`, `ensureCoaEstimateColumn`, `ensureJournalReferenceColumn` (`src/api/routes/accounting.ts`), `ensureOrgPhotoColumns` (`src/api/routes/org-chart.ts`) and `ensureDeductionSourceColumn` (`src/api/lib/attendance-deduct.ts`) called `db.prepare(ALTER …).run()` directly. `ensurePvApprovalCols` also dropped and re-added `payment_vouchers_status_check` every round; the ADD re-checks every row under the lock.
- **Fix:** those rounds send their ADD COLUMN and CREATE INDEX statements through `runSelfApply`. The PV rounds keep swallowing failures, as before. The status CHECK is rebuilt only when `pg_get_constraintdef` shows it does not already allow `'DRAFT'` (or the read fails). The `approval_state` backfill UPDATE is left unguarded: it takes row locks only, not ACCESS EXCLUSIVE, and matches no rows once backfilled.
- **Lock count per cold round, warm database:** `payment_vouchers` 24 → 0; `payment_voucher_allocs` 2 → 0; `chart_of_accounts`, `journal_entries`, `payroll_hour_deductions` 1 → 0; `users`, `workers` 1 → 0 each; `announcements` 11 → 0. A missing column is still added, as before.
- **Also fixed:** `delivery-agent.ts` already used `runSelfApply`, but five `ADD COLUMN` statements on `delivery_proposals` lacked `IF NOT EXISTS`, so the catalog filter could not recognise them and they ran every cold round. They now carry it. `ensureOrganisationRegistry` (`organisations.ts`) dropped `organisations_code_check` every cold round (runSelfApply cannot see constraints); it now drops it only while `pg_constraint` still has it.
- **Announcements:** `ensureAnnouncementsTable` (`src/api/routes/announcements.ts`) sent 11 raw ALTERs on `announcements`. The table and its index now go through a strict `runSelfApply` (a real failure throws, as before); the rest goes through one best-effort `runSelfApply` whose failure sets the retry flag, as each try/catch did before.
- **Regression test:** `tests/self-apply-no-raw-alter.test.mjs` — fails on any memoized round in `src/api` that sends a raw `ALTER TABLE … ADD COLUMN`; checks the status CHECK rebuild sits behind the DRAFT guard and the organisations DROP behind its `pg_constraint` read; and runs `ensureDeductionSourceColumn` against a catalog that already has the column and expects no ALTER.
