## BUG-2026-11-27-564 — Stock adjustment: duplicate-deduction gaps in server idempotency, and an adjuster taken from the client `inventory` `stock-adjustments` `idempotency` 🟡

> **Last verified: 2026-11-27**

**Status: OPEN. Not fixed.** The backend transaction logic is unchanged and a change needs owner approval.

- **Found by:** the Final Batch 5 mobile Inventory work (Reduce Stock), reading `src/api/routes/stock-adjustments.ts` and `src/api/lib/idempotency.ts` at upstream/main `e02e27f15`.
- **Duplicate-deduction risk:** `POST /api/stock-adjustments` is wrapped in `idempotent()`, but:
  - The entry lives in the `SESSION_CACHE` KV. If the binding is missing or a KV read or write fails, the middleware silently skips deduplication.
  - The in-flight sentinel lives 5 minutes.
  - A 5xx clears the slot. A write that committed and then answered 500 (e.g. "Failed to reload after insert") can therefore run again under the same key and deduct twice.
  - A 409 (below zero) is cached against the key for 24 hours. Retrying the same body replays it even after stock has risen.
- **Attribution:** `adjustedBy` / `adjustedByName` are read from the request body and not checked against the signed-in user.
  - The old mobile form (removed in Final Batch 5) sent neither, so past mobile adjustments show "—" for "By". Not measured.
  - The new mobile sheet sends them the way desktop does.
- **What the mobile UI does (not a server guarantee):**
  - An in-flight lock.
  - One Idempotency-Key per intent.
  - After an uncertain outcome, it re-reads the balance before allowing another submit.
  - It re-fetches the balance after success.
- **Fix options (to approve):**
  - Set the adjuster on the server from the session.
  - Make the idempotency slot survive a 5xx after commit, or record the key in the same DB transaction.
  - Fail closed when KV is unavailable.
- **Regression test:** to be written with the fix.
