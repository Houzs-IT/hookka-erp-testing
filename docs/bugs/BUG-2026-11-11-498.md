## BUG-2026-11-11-498 — Production Revenue priced production orders from the wrong order line `production` `accounting` 🟡

🟡 **On branch** (`fix/production-revenue-order-line` → `main`). Found 2026-11-11 while checking RM 0 prices for the owner (read-only on prod).

**Report.** November Production Revenue showed SO-2610-074's A01 at RM 0 / RM 0 and its SB02 at RM 180 / 80 / 150 / 0, while the sales order itself prices SB02 RM 180 × 4 and A01 RM 80 × 2 (total RM 3,130, measured on prod 2026-11-11). Finished so far the order is worth RM 2,530; revenue counted RM 2,060.

**Cause.** Every price lookup joined `sales_order_items.lineNo = production_orders.lineNo` (and the same for consignment lines). But the builder writes `production_orders.lineNo = poSequence`, a running PIECE number across the whole order (`_shared/production-builder.ts`, `poSequence++` per piece; non-sofa lines fan out one production order per unit). Once a line with quantity > 1 comes before other lines, every later piece points at the wrong line, or at no line (then the product master price, often empty, so RM 0). Sofa lines are one production order each, so sofa-only orders were unaffected. Same join in 6 places: `production-revenue.ts`, `dept-revenue.ts`, `dashboard-overview.ts` ×2, `working-hour-entries.ts` ×2 (Labor Cost tab, finance dashboard Cost Structure, dashboard Department Revenue and Production line).

**Fix.** New column `production_orders.source_line_no` (the real SO / CO line). `ensureProductionOrderSourceLine` self-applies it (migrations don't apply on deploy) and runs before the builder writes and before each of the 6 reads. The builder stores `item.lineNo`. All 6 lookups match on `PRODUCTION_ORDER_LINE_SQL` = `COALESCE(po.source_line_no, po.lineNo)`, so nothing changes until a row is filled. Old rows: `POST /api/production/order-lines/backfill-source-lines` (`?dryRun=true` first): per order it replays the builder's piece numbering and keeps a line only when the product code matches; orders numbered by line (older builder) are detected per order and kept on their line; otherwise the only line with that product; anything else stays unresolved and is listed. Each row is filled only while still empty; every row whose line moves gets an audit row (`backfill-source-line`, before / after line and price). Stock and service production orders don't link to a customer sales order and are left alone.

**Prod.** Not run. Needs this branch deployed, then the dry run (it reports how many rows move, unresolved ones and the price-basis change), then the owner's OK, because past months' Production Revenue, Department Revenue and Labor Cost figures change for the affected orders. Prod scale is UNMEASURED until that dry run.

**Guard.** `tests/production-order-line.test.mjs` (10 cases): SO-2610-074's 12 pieces map back to lines 1,2,3,3,3,3,4,4,5,5,5,5; old line-numbered orders keep their line; product fallback; unresolved; all 6 lookups use the shared expression and ensure the column; the builder stores `item.lineNo`; the backfill plan for SO-2610-074 moves 9 rows and RM 1,070 of price basis; dry run writes nothing; live run fills only empty rows and audits the 9 moved ones. `tests/repair-scope.test.mjs` column-list pattern updated for the new column.
