## BUG-2026-11-10-487 — two delivery returns, purchase returns or stock adjustments saved at once could take the same number `delivery-returns` `purchase-returns` `stock-adjustments` `numbering` 🟡

`nextReturnNo` (`src/api/lib/delivery-return-create.ts`), `nextPurchaseReturnNo` (`src/api/lib/purchase-return-create.ts`) and `nextAdjNo` (`src/api/routes/stock-adjustments.ts`) read the highest number and add one, with no retry, and the tables carry no unique index on the number (prod index state UNMEASURED). Two saves in the same instant both wrote e.g. `DR-2611-004`. Sister: Houzs#5546 (review pass 2, H3 B2). Found by code reading; whether prod holds duplicates today is UNMEASURED.

Fix: each insert batch opens with a transaction-scoped advisory lock on that table's numbering and a "number still free" check run after the lock (`src/api/lib/doc-no-guard.ts`); a clash raises `DOC_NO_TAKEN` and the save re-reads a fresh number and retries, up to five times. No index created, no existing row touched.

Regression: `tests/pass2-reliability.test.mjs` (B2 block); fakes in `tests/hk0110-delivery-return-caps.test.mjs`, `tests/t006-returns-main.test.mjs` updated for the two guard statements.
