## BUG-2026-11-10-444 — Cash Flow with Forecast on showed only its first few columns `accounting` `ui` 🟡

The owner's screenshot (2026-11-10): Cash Flow, Forecast pressed. The table showed Item, Accumulated, the two columns of Nov'27 and one of Oct'27; everything to the right was blank. The figures were right, the layout was not.

Cause: finance tables remember a dragged column width (`src/lib/use-resizable-tables.ts`). A report (`data-col-resize="first"`) keeps only its description column's width, under a key that names that column alone, so the width survives a change of period. The enhancer used the same key to decide whether the header had changed. With a dragged Item width, the 5-column statement (Item, Accumulated, three months) was pinned with a 5-column `<colgroup>` and a fixed table width. Pressing Forecast turned the same `<table>` into 35 columns under the same key, so nothing was laid out again: the five pinned columns took the whole fixed width and the other 30 shrank to zero. Without a dragged width nothing is pinned, which is why the forecast looked right in every check made without one. Reproduced on prod with a dragged width in the browser's storage: 35 cells a row, 5 `<col>`s, table 671 px, 30 columns 0 px wide. The same would hit any report whose columns change while it is open, Monthly P&L's Forecast toggle included.

Fix: the enhancer compares a layout signature (`colLayoutSig`: the width key plus every top header cell and its span). When columns come or go, the table is unpinned, measured again and pinned with the dragged description width put back. The width key itself is unchanged, so remembered widths still apply.

Regression: `tests/finance-tables-drills.test.mjs` ("a report lays out again when its columns come or go"). Class: C22 in `docs/BUG-CLASSES.md`.
