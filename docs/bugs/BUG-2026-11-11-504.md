## BUG-2026-11-11-504 — Edit Supplier refused to save, in silence, when the main Email held two addresses `procurement` `forms` 🟠

🟡 **On branch** (`fix/supplier-email-blocks-save` → `main`).

**Symptom.** Owner, 11 Nov 2026: 「Supplier term 我edit 了为什么save 不到」 — a supplier's Payment Terms were changed in Edit Supplier and Update did nothing. Reproduced on prod read only (the PUT intercepted in the page, nothing sent): for the one supplier of 41 whose main Email holds two addresses joined by " / ", changing the terms and pressing Update sent no request and left the dialog open. The only sign was small red text under the Email field at the top of the scrolling dialog; the buttons are at the bottom. For any other supplier the same steps send the right `paymentTerms`, and the page reads the supplier again after the save.

**Cause.** `SupplierFormDialog.handleSubmit` (`src/pages/procurement/supplier-form-dialog.tsx`) began with `if (!isValidEmail(email)) return;` — a bare return, no message where the user is looking. `isValidEmail` accepts one address only, while the main Email is a list on purpose: the PO email sends To every address in it (`poEmailRecipients`, `src/lib/supplier-emails.ts`). The input was also `type="email"`, whose browser check rejects a list as well.

**Fix.** `supplierMainEmailError` (`src/lib/supplier-emails.ts`) checks the main Email with the PO email's own split (comma / semicolon / new line, each piece one address) and returns a sentence saying how to fix it ("Separate several addresses with a comma, or put the second one in Email 2"). The dialog shows that sentence under the field, and a refused Update now shows "Can't save yet — …" beside the buttons and puts the cursor in the Email field. The Email input is a plain text field so the browser's single-address check does not block a valid list. The stored " / " email is left as it is — the owner corrects it in the form.

**Regression.** `tests/supplier-main-email.test.mjs` (list rule, the slash refused with its sentence, agreement with the PO email split, the dialog never refuses in silence); `tests/contact-standardization.test.mjs` updated — it had pinned the silent return.
