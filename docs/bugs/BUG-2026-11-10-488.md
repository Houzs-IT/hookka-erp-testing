## BUG-2026-11-10-488 — two Approve presses on a payment voucher, or two PO saves a few ms apart, both passed an in-memory check `accounting` `purchase-orders` `race` 🔴

`pvApprovalCore` (`src/api/routes/accounting.ts`) checked `state !== "CHECKED"` in memory, then wrote `UPDATE payment_vouchers … WHERE id = ?` in the batch that builds the postings / AP settlement document — two presses at the same moment could both build them (journal legs were probably caught by `idx_lje_idempotent`, the settlement document was not traced). Every other rung had the same shape. The PO PUT compared `expectedUpdatedAt` in code (`editConflictMessage`) and then wrote `WHERE id = ?`, so a second save a few ms later silently undid the first. Sisters: Houzs#5532 / #5540 (H3 B3), Houzs#5564 (H3 B4). Found by code reading; prod occurrences UNMEASURED.

Fix: every PV rung writes `AND approval_state = <read state>`; single-statement rungs refuse on 0 changes, approve puts the CAS guard right after its UPDATE so the postings roll back with it (409 `status_changed`). The PO PUT batch, when the form sent `expectedUpdatedAt`, opens with a `FOR UPDATE` row lock that re-checks `updated_at` (to the ms) against the read value and refuses with the existing 409. The postings are built exactly as before.

Regression: `tests/pass2-reliability.test.mjs` (B3, B4 blocks).
