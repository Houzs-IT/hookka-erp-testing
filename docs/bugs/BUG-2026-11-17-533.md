## BUG-2026-11-17-533 — Mobile Employees: after Labor Cost loaded, the other tabs stopped responding (menu registration render loop) `employees` `mobile` 🟡
> **Last verified: 2026-11-17** against `src/pages/m/screens/employees/EmployeesRoute.tsx`, `LaborCostSection.tsx`, `use-labor-cost.ts` and `tests/m-employees-menu.test.mjs` (branch `fix/employees-menu-render-loop`, to `staging`). Reproduced and fixed on sample data only.

🟡 **On branch** (`release/hk0125-employees-main` → `main`; staging PR #1424, which numbered this BUG-2026-11-17-525 before main's #1425 took that number). Introduced by #1422 (the Employees "..." menus). **Staging verification is still pending**: the fix has only been run against the local sample server; the main release is held until it is checked on staging.

**Symptom.** On staging mobile, Employees tabs switched normally until Labor Cost was opened. Once its data loaded, tapping Efficiency, Department Labor, Employee Performance or Payroll did nothing: the URL changed but the tab bar stayed on Labor Cost, and the console filled with "Maximum update depth exceeded".

**Root cause.** Each section registers its menu items with the shell through `bridge.set(...)` inside an effect (`menu-context.ts`). The shell (`EmployeesRoute.tsx`) stored the registry object in state, so every registration re-rendered the shell, which re-rendered the open section, which re-ran its registration effect. That is only safe if the effect's dependencies are stable. Labor Cost's effect depended on `result` (`computeLaborCost(...)` run inline on every render) and, once that was memoised, on `revenue.value`, which `use-labor-cost.ts` also rebuilt as a new object on every render. Memoising `result` alone did not stop the loop. Efficiency and Employee Performance build their data the same unmemoised way; they likely shared the latent loop (not confirmed), and the shell change below covers them.

**Fix.** `LaborCostSection.tsx` memoises `result`. `use-labor-cost.ts` memoises the revenue value on the response and shares one empty holiday list instead of a new `[]` per render. `EmployeesRoute.tsx` keeps only the SHAPE of the registered menu (which actions, busy, note) in state and the run closures in a ref, so re-registering the same actions is a no-op for any section, present or future.

**Class.** None in `BUG-CLASSES.md` fits (an effect dependency that is a new object every render, feeding state that re-renders the effect's own component); the guard test below pins the design.

**Regression.** `tests/m-employees-menu.test.mjs`, "registering menu actions can never loop": the shell keeps the closures in a ref and only a string shape in state, Labor Cost's `result` is memoised, the revenue value is memoised on the response, and no fresh `[]` per render.

**Checked.** Sample data at 390px: Labor Cost with data loaded, then Efficiency, Department Labor, Employee Performance, Payroll and the other tabs all respond with 0 "Maximum update depth" errors; Print report and Settle month still appear when eligible; Print follows the latest period, category and search.
