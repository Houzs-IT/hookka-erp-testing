## BUG-2026-11-12-506 — re-importing an existing fabric code reset its fabric stock to 0 `inventory` `raw-materials batch import` 🟡

**Found:** 2026-11-12, while checking HK-0142 (bulk-create fabric codes) on a local database. Not reported by a user.

**What happened:** Inventory → Raw Materials → Batch Import, with a row for a fabric code that already exists
(item group B.M-FABR / S.M-FABR / S-FABRIC). `raw_materials.balanceQty` was kept, as designed, but the
mirror rows were rewritten with stock 0: `fabrics.sohMeters` and `fabric_trackings.soh`. Measured locally:
SIENNA 02 at 12.5 m → re-import with a new description → raw_materials 12.5, fabrics 0, fabric_trackings 0.

**Cause:** the bulk-import route called the fabric cascade with a hard-coded `balanceQty: 0` for every row,
new or existing (`src/api/routes/raw-materials.ts`, bulk-import loop). The cascade writes that value on UPDATE.
The single create / edit paths pass the real balance and were not affected.

**Fix:** `buildFabricUpsertStatements` takes an optional `balanceQty`. Omitted, an existing mirror row keeps
its stock and a new one starts at 0. Bulk import omits it for existing codes and passes 0 for new ones.

**Prod impact:** UNMEASURED. Any fabric code re-imported before this fix may have a mirror stock of 0 while
its raw material holds stock. A check for YH to run (read-only):
`SELECT rm.item_code, rm.balance_qty, f.soh_meters FROM raw_materials rm JOIN fabrics f ON f.code = rm.item_code WHERE rm.item_group IN ('B.M-FABR','S.M-FABR','S-FABRIC') AND rm.balance_qty <> f.soh_meters;`
(column names checked against `column-rename-map.json` and a locally migrated schema; the query was not run on prod).

**Test:** `tests/rm-bulk-import-keeps-fabric-stock.test.mjs`.
