## BUG-2026-11-19-535 — Outsource Fabric: "Could not load workers" on the first open after deploy (concurrent table setup) `production` `outsource` 🟡
> **Last verified: 2026-11-19** against `src/api/lib/outsource-issue.ts` (`ensureOutsourceIssueTable`, `runCreateStatement`) and `tests/outsource-issue-table-setup.test.mjs` (branch `fix/hk0164-ensure-ddl-race`, to `staging`).

🟡 **On branch** (`fix/hk0164-ensure-ddl-race` → `staging`). Introduced by #1460 (HK-0164).

**Symptom.** Right after #1460 reached staging, the first open of Production → Outsource Fabric showed "Could not load workers: Something went wrong on our side" (a 500 from `GET /api/outsource-issues/workers`). Measured on staging a few minutes later, signed in: `/api/outsource-issues/workers` 200 (3 workers), `/api/outsource-issues?status=INCOMPLETE` 200, `/api/kv-config/outsource_issue.enforce` 200. It did not come back.

**Root cause.** The page loads the workers, the issue list and the switch at the same time, and every one of those handlers awaits `ensureOutsourceIssueTable` first. The boolean memo is only set after the statements land, so on the very first load several requests run `CREATE TABLE IF NOT EXISTS outsource_issues` and its `CREATE INDEX IF NOT EXISTS` statements together. In Postgres, two concurrent `IF NOT EXISTS` creates of the same relation can still fail the loser with `23505` (`pg_type_typname_nsp_index`) or `42P07`. The global error handler turned that into the generic 500. Once the table existed, `IF NOT EXISTS` is a no-op and the error stopped. The server log line (`[onError <ref>]`) was not available, so the exact SQLSTATE of this occurrence is UNMEASURED; the mechanism is read from the code and matches the symptom (a non-transient 500 that healed by itself, not the 503 a database blip gets).

**Fix.** Each setup statement is retried once when it fails with a concurrent-create code (`23505`, `42P07`, `42710`); on the retry `IF NOT EXISTS` sees the other request's table and does nothing. Any other error still fails loudly and the next request tries again. The memo stays a boolean set only after every statement lands: a shared promise would hand one request's socket to the others (BUG-CLASSES C9, BUG-2026-10-19-334).

**Class.** Next to C9 (runtime self-apply). Not a C9 instance: the memo shape was already the C9-correct boolean; the gap is that a boolean memo lets parallel first requests race the DDL. Every other `CREATE TABLE IF NOT EXISTS` self-apply has the same first-load race; not swept here.

**Regression.** `tests/outsource-issue-table-setup.test.mjs`: two parallel first requests both succeed when one loses the create race; a concurrent create from another isolate is retried once; any other error rejects and the next call retries; the memo is a boolean. The first two fail on the code before this fix.

**Checked.** Unit tests and typecheck. UNMEASURED: the race itself on real Postgres (it only happens while the table does not exist yet, which on staging is already past; prod has not had its first load).
