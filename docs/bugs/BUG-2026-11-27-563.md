## BUG-2026-11-27-563 — Pending-invite list returns the raw invite token to non-Super-Admins `users` `security` `rbac` 🔴

> **Last verified: 2026-11-27**

**Status: OPEN, URGENT. Not fixed.** The backend fix needs separate owner approval.

- **Found by:** the Final Batch 5 mobile User Management audit, reading the code at upstream/main `70fdb867e` / `e02e27f15`.
- **Symptom:** `GET /api/users/invites` (`src/api/routes/users.ts`) is gated by `requirePermission(c, "users", "read")`. `publicInvite()` returns every pending invite's raw `token`.
  - `users:read` is held by roles other than Super Admin (ADMIN, OFFICE and HR in the code-defined policy). Live grants are UNMEASURED.
  - The token alone lets anyone open the public accept-invite page, set a password and be signed in with the invite's role. That includes a pending SUPER_ADMIN invite, which bypasses the Super-Admin-only invite rule.
- **Also exposed on desktop:** the desktop `/settings/users` page reads the list through `useCachedJson`, so the tokens are also stored in the browser's localStorage.
- **What the mobile redesign did (not a fix):** Final Batch 5 stops mobile from adding exposure.
  - The mobile screen is Super Admin only.
  - Invites are read with a plain fetch and the token is kept in memory only.
  - The invite-token route is gone.
  - Global Search no longer reads `/api/users/invites`.

  The server still sends the token to every `users:read` holder.
- **Fix options (to approve):**
  - Return `token` only to SUPER_ADMIN; or
  - key resend / revoke by a public invite id and never return the token in a list.

  Either way, stop the desktop page caching the list in localStorage.
- **Regression test:** to be written with the fix. It should assert that a non-SUPER_ADMIN `GET /api/users/invites` carries no `token`.
