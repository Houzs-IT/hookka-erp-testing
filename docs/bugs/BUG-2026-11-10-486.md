## BUG-2026-11-10-486 — a late Delivered / Dispatched tap could bring a cancelled DO or consignment note back `delivery-orders` `consignment-notes` `race` 🔴

`applyDeliveryOrderUpdate` (`src/api/routes/delivery-orders/_helpers.ts`) read the DO, checked `VALID_TRANSITIONS[existing.status]` in memory, then wrote `UPDATE delivery_orders SET … status = ? … WHERE id = ?` in a batch that also held the stock-out / COGS / auto-invoice statements. A cancel that committed between the read and the write was overwritten: the DO came back as Delivered after the cancel had already returned its stock (stock overstated). Any plain edit landing after a cancel did the same, since the UPDATE always rewrites `status`. The consignment-note PUT (`updateConsignmentNoteById`) and the CN return (`POST /:id/return`, a double tap returns stock twice) had the same shape. Sister: Houzs#5528 (cross-system review pass 2, H3 B1). Found by code reading; whether it ever happened on prod is UNMEASURED.

Fix: the DO UPDATE matches only the status it read, and a guard statement right after it (`casGuardSql`, `src/api/lib/status-cas.ts`) divides by zero when nothing matched, so the whole batch rolls back → 409 `status_changed` naming the current status. CN PUT: `AND status IS NOT DISTINCT FROM ?` + refuse on 0 changes, before any cascade. CN return: the existing `FOR UPDATE` lock also checks the status, and a second guard (run after the lock is held) checks the quantity still out. Refuses a conflicting write only.

Regression: `tests/pass2-reliability.test.mjs` (B1 block).
