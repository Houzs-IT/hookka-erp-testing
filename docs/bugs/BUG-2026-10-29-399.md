## BUG-2026-10-29-399: Two edits of one received GRN moved stock by the wrong qty; draft save dropped PO links; a return after billing blocked the invoice `grn` `purchase-returns` 🟡

🟡 **On branch** (`fix/grn-edit-race-and-return-cap` → `main`). Found in a review of past ticket fixes (HK-0108, HK-0107, HK-0096), 2026-10-29.

**Symptom.** (1) A received GRN line accepted at 10: user A saves 12, user B saves 15, both read 10. The line ends 15 but stock, ledger and PO received move +7. (2) A draft GRN save that sent a line id no longer stored (after another user's delete-and-reinsert) silently lost that line's PO link; a blank id counted as a real id; with no ids and a changed line count, links were matched by position. (3) A purchase return made from a GRN after the line was billed counted as "returned before billing", so re-saving that purchase invoice got 409.

**Cause.** (1) `PUT /grn/:id` computed the delta from the qty it read, but the line UPDATE had no check on it; the RM batch update wrote a precomputed value. (2)(3) `grn.ts` draft path trusted `item.id != null` and `oldLines[i]`; `checkPurchaseReturnQty` capped a GRN return at accepted, not at the unbilled part.

**Fix.** Line UPDATE raises `grn_line_race` when stored acceptedQty changed since the read (409, reload); batch update adds the delta in SQL. Draft: blank id = missing, id not found = 409, position match only when line count unchanged. GRN returns capped at accepted − invoiced − earlier GRN-only returns.

**Regression.** `tests/grn-posted-edit-line-pairing.test.mjs`, `tests/grn-pi-edit-keeps-line-po.test.mjs`, `tests/purchase-return.test.mjs`.
