## BUG-2026-10-29-399: Same production order could land on two live DOs, and a delivery return could be restocked and cancelled at once `delivery-orders` `delivery-returns` 🟡

🟡 **On branch** (`fix/do-duplicate-race-and-return-status` → `main`). Found in a review of past ticket fixes, 2026-10-29. Not seen on prod.

**Symptom (by reading the code).** Two tabs creating a DO for the same production order with different idempotency keys: both duplicate checks (`validateDoComposition`) read "none", both saves commit. Separately, restock and cancel at once on one OPEN delivery return: both read OPEN, the restock credits stock, the cancel then writes CANCELLED, leaving a CANCELLED return whose stock was credited and whose qty is freed under the return cap.

**Cause.** Read-then-write with nothing in the DB enforcing it. `delivery-returns.ts` status UPDATEs matched on `id` only; `mark-redelivered` had no status check at all.

**Fix.** `src/api/routes/delivery-orders/_helpers.ts` save batch: per-PO `pg_advisory_xact_lock` then a raising guard (any PO on another non-CANCELLED DO), mapped to the same 409 text. `src/api/routes/delivery-returns.ts`: return-to-stock, set-outcome, cancel, mark-redelivered UPDATEs carry the from-status and a trailing raising check; a lost flip rolls the batch back and returns 409. `mark-redelivered` only from SERVICE_SPAWNED.

**Regression.** `tests/do-create-requires-production-orders.test.mjs`, `tests/hk0110-delivery-return-caps.test.mjs`.
