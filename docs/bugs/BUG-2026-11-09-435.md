## BUG-2026-11-09-435 — Saves that ignored a refused response, so the screen said "saved" when the server said no `customers` `sales` `inventory` `delivery` `ui` 🟠

Several save / delete actions sent the request and carried on without looking at the answer. When the server refused (validation, lock, permission, a linked record), the operator was told it had worked:

- **KYC panel** (`src/components/customer/KycPanel.tsx`) flashed the green "Saved" tick on any response.
- **CRM panel** (`src/components/customer/CrmPanel.tsx`) closed the contact form, cleared the activity form and reloaded after a refused add, and reloaded after a refused delete — the typed text was lost and nothing said why.
- **Consignment order delete** (`src/pages/consignment/detail.tsx`) navigated back to the list as if the order were gone.
- **Delivery Return → Repair & Redeliver** (`src/pages/delivery-returns/detail.tsx`) toasted "Service case opened" and navigated even when the service-case create or `/set-outcome` was refused.
- **Stock Value → Post all** (`src/pages/inventory/stock-value.tsx`) fired one PUT per DRAFT row and ignored every response; refused rows stayed DRAFT silently. **Initialise month** likewise.
- **Leads** (`src/pages/leads/index.tsx`): add, edit, move stage, delete, convert (hub + mark-won) and catalogue SKU add / remove.
- **Purchase Return delete** (`src/pages/purchase-returns/index.tsx`).

Related, same class: Consignment Note status actions and the SKU delete on Inventory checked `res.ok` but showed a fixed "Failed …" / "HTTP n" instead of the server's reason.

Fix: one helper, `responseErrorMessage(res, fallback)` (`src/lib/response-error.ts`), returns the body's `error` (or `message`) and only otherwise `"<fallback> (HTTP n)"`. Every site above now checks `res.ok` before its success path and toasts that message (`toast.error` still runs it through `humanizeError`, so a technical string never reaches the operator). Forms stay open with what was typed. Owner-approved FE quality batch A, item 16 (2026-11-08).

Class: the "an ACTION is a figure too" corollary in `docs/BUG-CLASSES.md` (same shape as BUG-2026-08-13-090, a form that never checked `res.ok` and closed as if saved).

**Batch B (2026-11-09, branch `fix/unchecked-saves-batch-b`).** A scan of every mutating `fetch` in `src/pages`, `src/components`, `src/lib` and `src/hooks` with no `res.ok` / `success` check found 40. Fixed (15): cash flow reconcile match and add transaction (`src/pages/accounting/cash-flow.tsx`); add employee, pay-rule save and delete, deduction undo, the two payslip regenerates after undo / settle-from-punches, leave add and approve / reject (`src/pages/employees.tsx`); PO mark-emailed (`src/pages/procurement/detail.tsx`); organisation deactivate and inter-company config (`src/pages/settings/organisations.tsx`); assistant pin and delete (`src/components/assistant/AssistantSlideOver.tsx`); and the BOM master migration (`src/pages/bom.tsx`), which deleted the legacy local copy even when the server refused the upload.

Left as they are, on purpose (best-effort, the caller must not block): logout, RUM beacon, presence ping, 2FA prompt dismiss, customer kv-config mirror, auto-dock from punch, party-alias learning, scan-sample feedback, scan-queue retry, BOM copy on SKU create, the assistant's background message save, the user dept/position mirror. The other hits already check the body further down (consignment note, mail compose / reply, SO create, service case / order create, delivery return create, rack stock-in, mailbox access).
