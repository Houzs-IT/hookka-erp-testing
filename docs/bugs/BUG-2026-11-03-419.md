## BUG-2026-11-03-419 — Daily Report "SO Without Invoice" counted SOs billed on a consolidated DO `reports` `compliance` 🟡

🟡 **Fixed on branch** (`fix/hk0127-so-no-invoice-consolidated-do`, to `main`). Ticket HK-0127.

**Symptom.** The Daily Report tile "SO Without Invoice" read 611 on production (2026-11-03; 613 from 2026-10-19, 142 before). Sampled rows such as SO-2603-039, SO-2602-040 and SO-2512-368 (Houzs Century) sit on DOs that carry a live SENT invoice.

**Root cause.** `checkSoNoInvoice` in `src/api/lib/compliance-report.ts` built `doIdToSoId` as a `Map<doId, soId>`. A consolidated DO lists several SOs through `delivery_order_items.salesOrderNo`, and each `set()` overwrote the last, so only one SO per DO saw the DO's invoice. Every other SO on that DO was flagged. Which SO survived depended on unordered row order, which is why the count jumped without a code change. 206 prod DOs carry more than one SO.

The same overwrite sat in `soIdByNo` (SO number → one SO id). Two SO numbers are each held by two DELIVERED rows on prod (SO-2512-368, SO-2603-157, from the 2026-04-22 tracker migration), and DO items carry only the number, so one row of each pair never reached its DO.

**Fix.** `doId → Set<soId>` and `SO number → [soId]`: an invoice on a DO marks every SO on it invoiced, and the delivered-date backfill feeds every SO on the DO. Replaying on prod data (read-only): old 611, DO set only 2 (the duplicate-number pairs), both fixes 0.

**Regression.** `tests/compliance-so-no-invoice-consolidated-do.test.mjs` (red on the old maps).
