## BUG-2026-11-10-443 — Header sort and funnel filters on paged lists judged one page only `sales` `procurement` `invoices` `ui` 🟡

Sales Orders, Purchase Orders, GRN and Invoices load one 200-row server page in their plain browse view. Each widened to every record for its filter bar and its search box, but the DataGrid's own header sort, column funnels and Group By This Column never reached the page. Once a list was longer than one page, sorting by amount gave the top of 200 rows, and a funnel gave the matches on that page only. Nothing on screen said so. Found by code reading for the 2026-11-10 cross-system review (G3; same class as Houzs#4753). Not reproduced in a browser.

Fix: DataGrid fires `onColumnViewChange(active)` while a header sort, column text filter, value filter the operator touched, or grouping is on (`columnViewActive`, `src/lib/grid-layout.ts`). SO / PO / GRN add it to the flag that already switches them to the whole-list fetch, the same path the search box uses. Invoices has no whole-list fetch (the server pages at 500), so the grid gets `totalRows` and shows "Column sorting, filters and grouping cover the 200 loaded rows of N" with a "Load all N" button that pages through every match (same query as Export). A page's own `defaultExcludedValues` does not count, otherwise /sales would always fetch everything.

Consignment Orders had the same 200-row page and widened for its filter bar only — not even for the search box. Both the search box and the column view now join its `_filtersActive`.

Not changed: the DO list (50 rows per stage tab) and the CN list (pages globally) carry the same limit. DO's grid mixes browse and search rows, so a total-vs-loaded notice would misfire there. Both are noted as follow-ups.

Regression: `tests/grid-common-features.test.mjs` (G3 block).
