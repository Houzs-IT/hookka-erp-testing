## BUG-2026-11-11-497 — Job cards still show 0 production minutes after their BOM / WIP Times minutes were filled `production` `bom` 🟡

🟡 **On branch** (`fix/bom-minutes-fill-zero-cards` → `main`), pushed, no PR yet (owner 2026-11-11: owner opens the PR). Second time for this class: BUG-2026-10-05-256 ran a one-off fill and left the cause open ("a BOM edit still does not reach existing cards").

**Report (owner, screenshot 2026-11-11).** Production sheets show Prod Time 0 while WIP Times has minutes for the same step: Fab Sew BC05 = 0 min, Upholstery 5567 = 0 min (SO-2610-283 cards, shown DONE).

**Cause.** A job card copies its BOM step minutes once, when it is created (`production-builder.ts` / `jobcard-sync.ts` insert `estMinutes` into `productionTimeMinutes`). WIP Times (`PUT /api/wip-times`, `POST /api/wip-times/bulk-import`) and Edit BOM (`PUT /api/bom/templates/:id`, `POST /api/bom/templates/bulk-process-edit`) only write `bom_templates`. So a card cut while its BOM step was 0 keeps 0 forever, and every BOM filled late makes a new batch of them. Prod state for BC05 / 5567 is UNMEASURED: the browser pane was not signed in to erp.hookka.com and there are no DB credentials in this session.

**Fix.** The fill logic moved out of the route into `src/api/lib/fill-zero-minutes.ts` (`planZeroMinuteFills`, `writeZeroMinuteFills`, `bomMinutesForCard`), and the expected-card builder into `src/api/lib/expected-job-cards.ts`. All four minute-saving routes now pass the saved BOM before and after the save to `syncJobCardMinutesToBomChanges` (`src/api/lib/bom-edit-card-sync.ts`). It reads that product's cards that are LIVE (WAITING / IN_PROGRESS / PAUSED / BLOCKED) or were completed this Malaysian month (`completedDate >=` the 1st, `currentMonthStartMY`; owner 2026-11-11: this month's payroll and efficiency are not calculated yet), never CANCELLED, and for each card works out its minutes under the old and the new BOM (same matching rules as BUG-2026-10-05-256, `bomMinutesForCard`). `decideCardMinutes`: a card at 0 gets the new minutes; a card whose step the save changed (old BOM minutes ≠ new) follows the new minutes, even if it had different minutes before (owner follow-up 2026-11-11: "if update wip times that already exist then change unfinished and finish current month"); a card on a step the save did not change keeps its minutes; a step set to 0 never zeroes a card. Only an ACTIVE BOM drives cards (a DRAFT edit touches none; WIP Times only edits ACTIVE BOMs). Each write re-checks the minutes it read (`WHERE … COALESCE(productionTimeMinutes, 0) = <read value>`) and is audited `sync-minutes-from-bom-edit` (before / after, source `system`). Cards completed before this month are never touched (pay already ran). The save response carries `jobCardMinutes` (`{ updated, scanned }`, or `{ error }` if the update failed; the BOM save itself still succeeds and the error is logged). The WIP Times Excel dry run touches nothing. **Preview before save (owner 2026-11-11, option 2):** the same plan runs without writing (`previewJobCardMinutesForBomChanges` → `jobCardPreview: { toUpdate, unfinished, completedThisMonth }`, or `{ error }`): `POST /api/wip-times/bulk-import` with `dryRun: true` returns it, and `PUT /api/bom/templates/:id?preview=true` returns it without saving the BOM. WIP Times single edit and batch edit (via the import dry run) and Edit BOM Save ask "Update job card times?" with that split before saving (shared `useConfirm`, helper `src/lib/job-card-impact.ts`); 0 cards = no question; a failed preview asks "Save anyway". The Excel import preview shows the same split (`JobCardImpactNotice`).
